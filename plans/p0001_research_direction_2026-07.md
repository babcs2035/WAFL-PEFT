# p0001: WAFL-PEFT 今後の研究方針（2026-07-26 策定）

Iter1〜12 の結果と，先行研究の再調査（tavily）に基づく次フェーズの研究方針である．
既存の判定を敵対的に再検討した結果，**これまでの結論の大半が測定ノイズの範囲内であった**ことが判明したため，
新しいレバーを振る前に測定系そのものを立て直す方針とする．

- 対象: `src/client.py`，`config/settings.json`，評価経路（`src/compare_runs.py` ほか）
- 前提: 実機 wafl500〜509（RTX 3060 12GB × 10 台，空き VRAM 約 8.4GB/台）．
  Iter12 を止めていた外部 GPU 競合は 2026-07-26 時点で解消済み．

## 1. 決定的な発見（既存結論の再検討）

### F1. 評価解像度が不足しており，Iter1〜12 の判定の大半が統計的に成立しない

評価サンプル数は 40〜80 問である．accuracy p≈0.225 における二項分布の標準誤差は次のとおり．

| n | SE | Wilson 95% CI 幅 | 80% power で検出可能な最小差 |
|---:|---:|---:|---:|
| 40 | 6.60pt | ±12.9pt | **26.2pt** |
| 80 | 4.67pt | ±9.2pt | **18.5pt** |
| 250 | 2.64pt | ±5.2pt | 10.5pt |
| 1319（GSM8K test 全体） | 1.15pt | ±2.3pt | 4.6pt |

`config.yml` の成功条件は「ノイズ（±5pt）を超えて +2pt 以上」であるが，n=80 の時点で +2pt の検出には
1 群あたり約 6,843 問（対比較でも約 1,962 問）が必要であり，**この条件は原理的に判定不能である**．

個別に検算すると:
- ベスト構成の +14pt（8.5% → 22.5%）: n=80 で z = 2.49（p ≈ 0.013）．辛うじて有意．
- ノード別 22.5% vs マージ 25.0%（+2.5pt）: z = 0.37（p ≈ 0.71）．**ノイズと区別できない**．
- Iter11 の rank32「大幅悪化」（22.5% → 16.2%，差 6.3pt）: z ≈ 1.0．**棄却判断の根拠が不足**．
- Iter6（接触窓 3000s）・Iter9（lr_min_ratio）・Iter10（dropout）の微差: すべて識別不能．

したがって「小シャード（~1345 サンプル）由来の過学習限界で収束した」という Iter11 時点の判定は，
**データが示した結論ではなく，評価解像度の不足によって差が見えなかっただけ**である可能性が高い．

参考: Bowyer, Aitchison, Ivanova, *Position: Don't Use the CLT in LLM Evals With Fewer Than a Few
Hundred Datapoints*, ICML 2025 Spotlight（arXiv:2503.01747）は n < 数百で CLT ベースの誤差棒が
不確実性を大幅に過小評価すると示している．Miller, *Adding Error Bars to Evals*（arXiv:2411.00640）も
power analysis の実施を推奨する．

### F2. マージ実装が WAFL の定式化から乖離している（自ノードを含まない完全上書き）

`src/client.py:882-902` の `merged` は，受信バッファにある **remote peer の重みのみ**を平均する
（`count` に自ノードが入らない）．そして `src/client.py:1151-1155` で

```python
param.copy_(merged_weights[name].to(param.dtype).to(param.device))
```

とローカルパラメータを**完全に上書き**する．接触相手が 1 台の場合（RWP のペア接触では通常こうなる），
これは平均ではなく**相手ノードの重みへの置換**であり，直前のマージ以降に自ノードが行った学習は
すべて破棄される．

WAFL 原典（Ochiai, Sun, Jin, Wongwiwatchai, Esaki, *Wireless Ad Hoc Federated Learning*,
arXiv:2205.11779）の定式化は自ノードを含む平均であり，本実装はこれと異なるアルゴリズムになっている．
ADF-LoRA（arXiv:2511.18291）も接触ペアの集約を "symmetric LoRA averaging" と記述している．

この乖離は，これまでの複数の観測を統一的に説明しうる:
- 接触窓を 1500s → 3000s に広げると悪化した（Iter6）→ マージ回数が増え，破棄される学習量が増えた
- LoRA rank を上げると悪化した（Iter11）→ 学習容量を増やしても上書きで捨てられる

ただし F1 のとおり，これらの観測自体が統計的に確定していない点には注意が必要である．

### F3. LoRA A の初期値がノード毎に異なる

`src/client.py:1523` で `set_deterministic_seed(PEER_ID)`（seed = base_seed + peer_id，`:167`）を
呼んだ後に `initialize_model()` が `kaiming_uniform_` で `lora_A` を初期化する（`:355`）ため，
各ノードの A は独立な乱数行列になる．中央集権 FL では毎ラウンド同一の A が配布されるためこの状況は
生じない．独立な kaiming 行列を n 個平均すると振幅が概ね 1/√n に縮む（数学的帰結）．
LoRA-FAIR（arXiv:2411.14961）は初期化整合性の重要性を "Client-Side Initialization Drift" として
指摘している（ただし扱っている状況は中央集権 FL であり同一ではない）．

### F4. ベースライン 8.5% が低すぎる疑い

`config/settings.json` の `model_id` は `google/gemma-4-E2B` である．Gemma 3n E2B の IT 版は
MGSM 0-shot 53.1%，HiddenMath 27.7% と報告されている（Google model card）．
PT 版でも Gemma-2 2B が GSM8K 5-shot 23.9% である．**8.5% というベースラインはこの水準から見て低く**，
「+14pt の改善」ではなく「壊れた状態からの部分回復」を測っている可能性がある．

疑うべき原因（優先順）:
1. **`max_seq_len: 208` が GSM8K の CoT を切り詰め，学習時に最終回答トークンが現れていない**
   → **2026-07-26 に実測で確認．下記 F5 を参照**
2. 回答抽出の正規表現の不一致
3. PT 版 / IT 版の取り違え
4. 4-bit 量子化による劣化（IJCAI 2025 は Llama-3.2-1B で 4-bit により GSM8K −25.3pt を報告）

### F5. 【実測確認済み】`max_seq_len: 208` は GSM8K 学習例の 32.5% で回答末尾を切り落としている

`cache/models/google/gemma-4-E2B` のトークナイザーと `cache/datasets/gsm8k/main/train-*.parquet`
（7,473 件）を用い，`src/client.py:396-416` の `tokenize_dataset` と同一の前処理
（`prompt = "Question: {q}\nAnswer:"`，`full_text = prompt + " " + answer`）を再現して実測した．

GSM8K の `full_text` トークン長: 平均 188.1 / 中央値 175 / p75 225 / p90 282 / p95 319 / p99 397 / 最大 543

| max_seq_len | 完全切り詰め（除外される） | **部分切り詰め（回答末尾が欠落）** | 無傷 |
|---:|---:|---:|---:|
| **208（現行）** | 1 (0.0%) | **2,428 (32.5%)** | 5,044 (67.5%) |
| 256 | 0 | 1,118 (15.0%) | 6,355 (85.0%) |
| 320 | 0 | 364 (4.9%) | 7,109 (95.1%) |
| 384 | 0 | 93 (1.2%) | 7,380 (98.8%) |
| **512** | 0 | **3 (0.0%)** | 7,470 (100.0%) |

`src/client.py:414` は **回答が完全に失われた例のみ**を除外する（`prompt_len >= len(full_ids)`）．
**部分的に切り詰められた 32.5% の例は除外されず，そのまま学習に使われる**．GSM8K の回答は
末尾に `#### N` という最終回答マーカーを持ち，評価はこれを抽出して採点する．すなわち現行設定では
**学習例の約 1/3 が「最終回答を含まない CoT」として学習されている**．

これは 8.5% という異常に低いベースラインと 22.5% という頭打ちを説明する最有力の機序である．
`max_seq_len: 512` で切り詰めはほぼ完全に解消する（残り 3 件）．

トレードオフ: 208 → 512 は系列長 2.46 倍で活性化メモリが増える．空き VRAM は約 6〜8.4GB/台で
Iter8 当時（12GB）より少ないため，OOM する場合は 320（切り詰め 4.9%）を中間案とする．
**ただし VRAM 制約の本体は seq_len ではなく次の F6 である．**

### F6. 【実測確認済み】モデル重みの 54% は 4-bit 化されておらず，これが VRAM 制約の本体である

`cache/models/google/gemma-4-E2B/model.safetensors` のヘッダを直接読み，テンソル単位のサイズを実測した．

| テンソル | 形状 | dtype | サイズ |
|---|---|---|---:|
| `model.language_model.embed_tokens_per_layer.weight` | [262144, 8960] | BF16 | **4.375 GiB** |
| `model.language_model.embed_tokens.weight` | [262144, 1536] | BF16 | 0.750 GiB |
| （以下 Linear 層．最大でも 1 層 0.035 GiB） | | | |
| **embed 系合計** | | | **5.162 GiB** |
| **ファイル全体** | | | **9.543 GiB** |

Gemma 4 E2B は Per-Layer Embedding（PLE）を持つアーキテクチャで，`embed_tokens_per_layer` だけで
4.375 GiB を占める．**bitsandbytes が量子化するのは `nn.Linear` のみで `nn.Embedding` は量子化しない**ため，
この **5.162 GiB（全体の 54%）は 4-bit 化されず fp16 のまま VRAM に常駐する**．
量子化対象の Linear 部（約 4.4 GiB）が NF4 で約 1.2 GiB になっても，重みだけで合計約 6.4 GiB になる．
`src/client.py:289` の「4-bit で約 2.5 GiB」というコメントは PLE を勘定していない．

**これが因果の根本である**:

```
PLE が非量子化（5.16 GiB が fp16 常駐）
  → VRAM 逼迫（README L205-213 の「ピーク 9.5GB で全ノード OOM」）
  → 対策として max_seq_len を 208 へ削減（Iter8）
  → GSM8K 学習例の 32.5% で回答末尾（#### N）が欠落（F5）
  → 評価が要求する回答形式が十分に学習されない
  → ベースライン 8.5% / 頭打ち 22.5%
```

つまり「小シャード由来の過学習限界」とされていたものは，**アーキテクチャ選択に起因する VRAM 制約の
下流症状**である可能性が高い．対処は次の 3 択．

1. **PLE を CPU へオフロード**する（`device_map` で `embed_tokens_per_layer` を CPU に置く）．
   PLE はもともと高速ストレージ／CPU に置いて必要分だけ読み出す設計であり，E2B の「実効 2B」という
   呼称もこれを前提としている．最も筋が良いが実装リスクを伴う．
2. **PLE を持たないモデルへ変更**する（Qwen2.5-1.5B/3B 等．重み約 1.1〜2.0 GiB）．
3. 現状維持（seq 208 のまま）．F5 の 32.5% 欠落が残るため推奨しない．

### F7. デプロイされているのは PT（base）版であり，README の記述と食い違う

`cache/models/google/gemma-4-E2B/tokenizer_config.json` に `chat_template` が無く，`chat_template.jinja`
も存在しない（＝ IT 版ではなく PT 版）．一方 `README.md` は `gemma-4-E2B-it` を 4 箇所で参照しており，
`config/settings.json` の `model_id` は `google/gemma-4-E2B`（PT）である．
どちらが意図なのかを確認する必要がある．F5 の回答形式欠落と重なると，出発点の弱さが accuracy を
さらに押し下げる．

## 2. 提案するレバー（優先順）

**F1 が未解決のまま accuracy 系のレバーを振っても，結果は判定不能である．** したがって W1・W2 を
先行させ，そのうえで W3 以降のアルゴリズム改良に進む．

| # | レバー | 変更内容 | 根拠 | 実装コスト |
|---|---|---|---|---|
| **W1** | `eval_resolution` | 評価問題数を 40〜80 → **500 以上**（可能なら GSM8K test 全 1319 問）．全条件で同一問題集合を使い，McNemar 検定で対比較．Wilson CI を必ず併記 | F1 | 小（評価ループの上限値と集計スクリプト） |
| **W2** | `max_seq_len` | 208 → **512**．事前に GSM8K 学習例のトークン長分布を計測し，208 での切り詰め率を確認する | F4 | 小（設定値．ただし VRAM 要確認） |
| **W3** | `merge_include_self` | マージ式を `mean(neighbors)` → **`mean({self} ∪ neighbors)`** に変更し，WAFL 原典の定式化に戻す | F2 | 小（`client.py` の集約部 10 行程度） |
| **W4** | `skip_local_train_when_isolated` | 近傍が 0 のとき局所学習をスキップする | WAFL 原典が明示的に規定（「If \|nbr(n)\| = 0, this minibatch-based adjustment process should be skipped because it causes over-fitting to the local dataset」） | 小 |
| **W5** | `lora_exchange_scope` | 交換対象を `lora_A + lora_B` → **`lora_A` のみ**（FedSA-LoRA 型） | Guo+ ICLR2025（arXiv:2410.01463）．A=汎用知識・B=ノード固有という非対称性 | 小（merge のキーフィルタ 10 行未満） |
| **W6** | `alternating_merge_interval` | ADF-LoRA 型の交互更新．学習は T ラウンド毎に A 相 / B 相を切替，**マージは常に A・B 両方** | arXiv:2511.18291．10 ノード・ペア接触確率 0.1 という WAFL 相当設定での唯一の実測値 | 中（20〜30 行） |

Iter12（逐次＝同期バリア方式との throughput 比較）は**指標が wall-clock throughput であり，
F1 の統計的制約を受けない**ため，W1 の完了を待たずに実行してよい．GPU 競合は解消済みで，
`config/hosts.txt` を元の 5 ノード（.100/.102/.103/.108/.109）に戻せばデッドロックは解消する．

## 2b. 実験規模・設定の拡大（ノード数・モデル・データセット）

### ノード数 5 → 10

**WAFL 原典は n=10 である**（arXiv:2205.11779．MNIST 90% Non-IID を 10 分割）．原典の RWP 設定は
`rwp0500`（一辺 500m，到達半径 100m，pose 10 epoch）で，本プロジェクトの
`rwp_n05_a0500_r100_p10_s42.json`（a=500/r=100/p=10）と一致するが n だけが 5 である．
すなわち **10 ノード化は「精度を上げるレバー」ではなく「原典と同じ土俵に戻して比較可能性を得る」
という論文上の正当化として位置付けるのが妥当**である．

固定する量の選択（文献の作法）:

| 固定する量 | 文献での扱い | 本研究での可否 |
|---|---|---|
| **総データ量固定**（7473 を n 分割 → 10 ノードで 747/node） | 主流．arXiv:2503.20768 は "By maintaining the total dataset size and varying the number of clients" と明記．WAFL 原典もこれ | **主実験はこれを採用**．ただし「n の効果」と「シャード縮小の効果」は原理的に分離できない |
| シャードサイズ固定（1345/node → 総量 13,450） | ほぼ見当たらない | **GSM8K train は 7,473 問しかないため不可能**．データセット拡張（後述）とセットになる |
| 接触密度固定 | WAFL 原典は n 固定・面積可変でこの軸を扱う | 感度分析として a=750 を 1 条件のみ追加 |

Random Waypoint のペア接触率は `β ≈ 2wd·E[V*]/A` で **n に依存しない**（Groenevelt ら）ため，
面積・半径・速度を固定すれば n=10 でもペア接触率は不変，ノードあたり接触機会は約 2 倍になる．
一方で **600 step 中一度も会わないペアの割合は 0〜10%（n=5）から 4〜16%（n=10）へ悪化**する
（本プロジェクトの `src/generate_contact_pattern.py` を用いた実測）．

**反証（重要）**: 文献で有意な n 効果が観測されているのは 10→100→1000 という**桁スケール**であり，
5→10 の 2 倍程度で明確な差を報告した例は見つからなかった．評価を 1319 問に直しても最小検出差は
約 4.5pt であり，5→10 の効果がこれを超える保証はない．さらに総データ量固定ならシャードが半減し，
既存の診断（過学習）を悪化させる方向である．**優先度は W1・W2 より低い．**

比較可能にするための条件: n=5 側も同一パラメータで seed 42/43/44 の 3 本を測り直すこと
（現状は 1 seed のみでトポロジー由来の分散が不明であり，n=10 と比べようがない）．

### モデルの変更

F6 のとおり Gemma 4 E2B は PLE により重みの 54% が非量子化で残る．6GB 制約下では seq_len を
伸ばす余地がほぼない．代替候補:

| モデル | 4-bit QLoRA 時の重み目安 | 報告 GSM8K | 6GB で可否 |
|---|---:|---:|---|
| Gemma 4 E2B（現行，PT） | 約 6.4 GiB（PLE 5.16 GiB が非量子化） | 非公表 | 不可（seq 208 でようやく成立） |
| Qwen2.5-1.5B-Instruct | 約 1.1 GiB | **73.2** | 可（大きな余裕） |
| Qwen2.5-3B-Instruct | 約 2.0 GiB | **86.7** | 可 |
| Llama-3.2-3B-Instruct | 約 2.1 GiB | 77.7 (8-shot CoT) | 可 |
| Llama-3.1-8B-Instruct | 約 5.5 GiB | 84.5 | 条件付き（seq 512 は厳しい） |

**反証**: Qwen2.5-3B の 86.7 のような強いベースは**天井効果**を生み，「協調学習の上積み」が見えなくなる．
協調の効果を測る実験としては 1.5B（73.2）程度に留め，Non-IID を強めにする方が設計として妥当である．

### データセットの変更

10 ノード × 1345 サンプルを維持するには 13,450 問以上が必要で，GSM8K train（7,473 問）では足りない．

| 名称 | サンプル数 | 報告 FT 後 GSM8K | 13,450 を満たすか | 注意 |
|---|---:|---:|---|---|
| GSM8K train（現行） | 7,473 | — | 不可 | MIT |
| **MetaMathQA** | 395K | LLaMA-2-7B 66.5 / Mistral-7B 77.7 | 可 | GSM8K を rephrase/FOBAR/self-verification で拡張＝**問題分布が現行と連続**．GPT-3.5/4 生成派生のため商用可否要確認 |
| Orca-Math-200K | 約 200K | Mistral-7B で 86.81 | 可 | 分布が変わる．MSR-LA 系の商用制限 |
| OpenMathInstruct-2 | 14M（uniq 約 600K） | Llama3.1-8B で MATH +15.9pt | 可（要サブセット） | CC-BY-4.0 系 |
| MathInstruct | 225K | OpenFedLLM が FL 実験に採用 | 可 | — |

**推奨は MetaMathQA**．GSM8K 由来の拡張なので過去 12 イテレーションとの問題分布の連続性が最も高い．
なお MetaMath の公式 SFT 設定は **max length 512** であり，F5 の測定結果と一致する．

**タスク自体を変える必要はない．** OpenFedLLM（KDD'24）や FedLLM-Bench（NeurIPS'24）といった
分散 FL の LLM 標準ベンチマークでも GSM8K は評価軸として使われている．ただし OpenFedLLM は
「各クライアント 5K サンプル」であり，現状の 1,345 は 1/4 未満である．**協調効果を出したいなら
「タスクを易しくする」より「1 ノードあたりのデータを増やす」方が文献の標準に近い．**

### 推奨する順序

複数を同時に変えると Iter1〜12 との比較可能性が完全に失われるため，**1 イテレーションに 1 レバー**とする．

1. **W1（評価 500〜1319 問）** — これ抜きでは以降すべて判定不能
2. **W2（seq_len）** — F5 の 32.5% 欠落の解消．OOM するなら先に F6 の PLE オフロードを試す
3. **W3（マージに自ノードを含める）** — WAFL 原典への準拠
4. データセット（MetaMathQA）→ 5. ノード数 10 → 6. モデル変更

固定し続けるもの: Non-IID 分割の seed とアルゴリズム，RWP パラメータ，評価プロトコル
（`####` 抽出，`max_new_tokens=256`），LoRA rank16/alpha32．

## 3. 敵対的検討（各案への反証）

- **W5（FFA/FedSA 系）への反証**: RoLoRA（NeurIPS 2025）は非 IID 下で FFA-LoRA が素の LoRA を
  下回る例を報告している（MNLI: 81.19 → 75.60）．A の凍結は表現力を落とすため，rank16 という
  小さな設定では逆効果になりうる．また FedSA-LoRA の GSM8K での報告改善幅は +0.40pt
  （LLaMA3-8B・3client・IID）と小さい．
- **W6 への反証**: RoLoRA の +15pt は**分散環境では再現していない**．ADF-LoRA 論文の DFL 表では
  RoLoRA 0.8284 < 素の LoRA 0.8458 と劣化する．サーバが凍結ブロックの同一性を強制できる前提に
  依存しており，サーバのない WAFL にそのまま持ち込むと逆効果になりうる．
  DFL 特化手法の改善幅自体も小さい（ADF-LoRA の平均改善 +0.47pt，TAD-LoRA は接続が密なら改善なし）．
- **W3 への留保**: 自ノードを含める変更は WAFL 原典への準拠であって，**改善が保証されるわけではない**．
  現行の「置換」方式でも +14pt は出ているため，置換ベースの拡散が機能していないとは言えない．
  W3 は「改善策」ではなく「原典との乖離の解消および仮説の切り分け」と位置付ける．
- **文献の適用範囲のずれ**: DFL 系（ADF/TAD）の検証は RoBERTa-Large 335M の GLUE 分類であり，
  2B 級モデルの GSM8K 生成タスクではない．**1345 サンプルという極小シャードで cross-term 対策が
  効くかを検証した論文は，今回の調査範囲では見つからなかった**．
- **spectral gap による定量化への反証**: Vogels+ NeurIPS 2022 *Beyond spectral gap* は「spectral gap は
  現実的にチューニングされた学習率下では性能を予測しない」と実験的に示している．説明変数としては
  使えるが予測指標として信頼してはならない．

## 4. 新規性の所在

WAFL 系の先行研究は**すべてシミュレーション**である（原典に "carried out the experiment by simulation
on a single computer" と明記）．また WAFL × LoRA/PEFT × 生成 LLM の組み合わせを直接扱った論文は
今回の調査範囲では見つからなかった．したがって本研究の固有の強みは以下にある．

1. **実機 10 台での wall-clock throughput の実測**（シミュレーションでは測れない）
2. **不均一な計算進捗・staleness の実機観測**（WAFL 系で未測定）
3. **接触トポロジーの定量指標と精度の対応付け**（WAFL 系は定性比較のみ）
